- 日期：2026-11-06 11:15
- 配置：configs/exp3b_b2a.json（运行前锁定）
- 数据：results/exp3b_b2a.json（3 次完整轨迹）、results/exp3b_b2a_explore12.json（探索性 12 轮，单独存放）
- 实验纪律声明：B2a 只测量**模型利用完整诊断信息的能力**。以下任何结果
  不得解释为"自主搜索能力提升"，更不得作为 RSI 证据。

## 一、预注册判定（先说结论，如实报告失败）

| 判定 | 阈值 | 结果 | 判定 |
|---|---|---|---|
| 主指标：最终提案命名 up_proj | ≥2/3 | **0/3**（三次均未提交提案） | **✗ 未通过** |
| 次指标：最终提案含真层 | ≥2/3 | 0/3（同上） | ✗ |
| 次指标：首次正确提案轮次 | ≤4 | 无提案 | ✗ |

**主指标失败原因（唯一）：模型在 10 轮预算内未调用 propose_edit。**
不是诊断错误——是流程没走到提案步骤。

## 二、过程指标：诊断行为发生质变（如实记录，不纳入判定）

三次正式运行 + 轨迹逐轮分析：

| 指标 | B1（历史基线） | B2a | 变化 |
|---|---|---|---|
| 首轮调用 | list_layers | **compare_all_projections**（1 次覆盖 252 单元） | ✓ 遵循指令 |
| 投影覆盖 | 100% 固着 q_proj（54/54 调用） | 全部 7 投影均有查询 | **根除投影盲区** |
| 病灶张量精确验证 | 0 次 | **3/3 次在 rounds 6-7 验证 (L22,up_proj) 与 (L28,up_proj)** | 0/3 → 3/3 |
| zero_rows 指纹利用 | 从未见过（没查过 up_proj） | 见到后立即定向验证 | ✓ |
| 验证后提案 | — | **3/3 未发生（预算耗尽）** | 新瓶颈 |

三次运行的 rounds 6-7 行为**完全一致**（贪心解码 + 相同提示下可复现）：
模型从聚合摘要正确读出 up_proj zero_rows=512，跳过 z 异常噪声，
直接对真病灶层做 tensor_stats 确认。

## 三、探索性归因（12 轮预算，1 次，不并入判定）

把预算 10→12（其余不变）后模型**仍未提案**：轨迹显示它转入逐一验证
天然 |z|>2.5 异常层（L0/L1/L2/L11 的 down/gate）——**验证狂热**：
学会了不轻信摘要，但没学会"指纹确认为主、z 异常为辅"的置信度分层，
也没有"留预算给提案"的策略。

## 四、科学结论（严格限定在 B2a 测量范围内）

1. **信息带宽是 B1 失败的直接原因**：同样的 4B 模型，从"54 调用 100%
   固着单投影"变为"1 次调用正确锁定 + 2 次调用精确验证病灶张量"。
   诊断所需信息本来就在权重统计里，B1 的工具架构让它不可达。
2. **新瓶颈是停止准则**：模型缺少"证据已足够，现在提交"的判断。
   这与 LLM 工具使用的已知问题一致（过度验证/不确定时继续收集）。
3. **对聚合工具两条改进**（给后续，本实验未测）：
   - 提示中显式给出预算分配模板（"1 扫描 + ≤3 验证 + 1 提案 ≤ 5 轮"）
   - 工具侧提案截止：剩余 2 轮时 harness 强制 "next call must be propose_edit"

## 五、工程记录：Windows mmap 崩溃链（0xC0000005）

实验三班期间连撞的 access violation 已定位并工程解决，过程留档：

- 现象：GPU 进程（transformers 加载检查点）内或之后，任何进程再 mmap
  同一 safetensors 即崩（三次复现：审计脚本、B2a runner、单元测试）
- 规律（对照实验确证）：父进程持 mmap → 子进程读同文件必崩；
  子进程单独读正常；纯 CPU 进程 inproc 读正常
- 根因：跨进程 safetensors mmap 冲突（Windows section 句柄，与今日
  环境 41 个 GPU 进程/驱动 610.60 共存可能相关——昨夜同代码正常）
- 解决：**预计算缓存**。聚合统计在 GPU 加载前由独立子进程算好落盘
  （results/_b2_cache/），运行期工具只读 JSON，零 mmap 交叉
- 附带修正：_SfReader 增加模块级缓存（acquire），单测改用缓存交叉对照
